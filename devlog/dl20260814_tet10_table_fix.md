# EF_TET10 Table Fix: MATLAB-First Regeneration of the Nédélec Second-Order Tables

**Date:** 2026-08-14
**Purpose:** Session record — root-cause and fix of defect D2 from the Nédélec extraction audit
(`todo/nedelec_edge_function_defects.md`): the `EF_TET10::precompute()` scalar and derivative
tables carried eta and zeta exchanged. Follow-on to `dl20260814_nedelec_tex_extraction.md`.
**AIs:** Claude (probes, MATLAB fix, C++ port), Christian (rulings, parallel MATLAB
verification, D1 in-tree fix)

## The booby trap, named

Christian identified the origin: on the EXODUS triangle, node k naturally carries the k-th
barycentric coordinate, so one assumes the tetrahedron continues the pattern. It must not: on
an EXODUS-ordered tet the naive map (node 2 with eta, node 3 with zeta) is left-handed,
`det J < 0`; the mathematically required map swaps them (node 1 carries zeta, node 2 carries
eta, `cl_IF_TET4.hpp`). Claude confirmed the handedness computation (naive map gives
`det[e01,e02,e03] = -1` in parameter space, swapped map `+1`). The trap is TET-specific, which
is why TRI3/TRI6 were clean and both defects (D1 in `EF_TET4::E`, D2 table-wide in
`EF_TET10`) sat in the tets. Recorded in `nedelec_derivation.md` §4 and in project memory.

## Root cause: one line in the table generator

The tables were generated by `tmp/tet10/tet10_generate.m`, which used the naive
`lambda = [xi; eta; zeta; tau]`, while its sibling cross-check `defelement.m` carried the
correct swapped map (its "careful, these are swapped" comments show the trap being fought
consciously at the edge level, but the generator line was never aligned). The C++ assembly
functions attach the gradients correctly for the Exodus edges and faces; only the scalar
tables were in the wrong convention.

## Fix chain, each stage gated

1. **Generator:** `tet10_generate.m` line 5 corrected to `lambda = [xi; zeta; eta; tau]`,
   with a booby-trap comment.
2. **MATLAB pins re-pinned:** the hand-optimized mirrors of the C++ tables in
   `tet10_function.m` (mG/mH/mU/mV/mW; also fixed the 12-vs-8 active-row face comparison) and
   `tet10_derivatives.m` (nine derivative tables) rewritten; all residual vectors
   `expand(generated - pinned)` exactly zero under Octave/SymPy, **and independently
   reproduced by Christian in MATLAB with the Symbolic Toolbox** (engine independence closed).
3. **C++ port:** the 14 tables in `EF_TET10::precompute()` (`cl_EF_TET10.cpp`) replaced with
   the re-pinned values; the redundant third face-candidate rows filled by the verified
   pattern (U-third = U-second, V-third = V-first, W-third = -2 x W-first). Assembly
   functions untouched; they were reviewed and are correct throughout (`compute_edge_*`,
   `compute_face_*`, the `C()` chain rule).
4. **Acceptance gate on the edited file itself** (`scratchpad/tet10_port_gate.py`): the C++
   table text is parsed back into sympy (exact rationals; a first run with float literals
   produced 1e-15-crumb false violations, fixed in the parser) and passes all four checks:
   scalar tables == generator truth; all nine derivative tables == exact derivatives; exact
   block-identity edge circulation plus zero face leakage on a random rational tet; and the
   `C()` chain-rule assembly == symbolic curl for all 24 dofs.
5. `g++ -fsyntax-only` with the build tree's own flags (Blaze+MKL): clean.

## Method note

The decisive discipline was Christian's: fix the *source of truth* (the MATLAB generator)
rather than patching the C++ by hand, and let the pinned-table pipeline regenerate the code
text. The original defect existed precisely because the generator and the hand-written
assembly conventions diverged without a gate between them; the re-pinned pipeline plus the
parse-back probe now form that gate.
