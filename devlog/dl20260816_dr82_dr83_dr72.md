## DR-82 — HDF5 loaders trusted the file's datatype

All four loaders in `hdf5_tools.hpp` passed the FILE datatype to `H5Dread`
as the MEMORY type, so a width mismatch between writer and reader builds
(`BELFEM_INT64` on one side only) copied at the file's element size —
silent overrun or silent uninitialized upper halves. Fixed with ladder
rungs 1+2 together: the reads now pass `datatype<T>()` as the memory type
(HDF5 converts widths, mixed-width files become readable), and a new
always-active `check_read_datatype<T>()` refuses the case conversion
cannot fix — a datatype-CLASS mismatch. The old class check was a
`BELFEM_ASSERT`, absent exactly in the release builds where this bites.
Writers untouched; rung 3 (fixed-width file types on create) is a
separate round, with a note there that the writers' LE-copy memory type
is little-endian-host-only (latent, no BE target).

All four `#ifdef BELFEM_DEBUG` sites flipped to `#ifdef DEBUG` on

## DR-72 — the register row over-priced its own remedy

Christian routed the analysis to a fresh Fable session (read-only). Its
central finding contradicts the row: the increment form is NOT an
IWG_Timestep change, because the Newton branch of `SolverData::solve`
already solves `J*delta = r` and updates `value -= omega*delta` — only
the **Picard branch** solves the absolute system, and the thermal kernel
runs Picard-first. The minimal fix (A′) restructures that one branch to
the residual/increment form: algebraically identical to the relaxed
Picard update, but the Krylov rtol then measures the increment scale.
Dof values stay absolute; BCs, rejection/reset, warm restart untouched;
Anderson staging becomes `R = -delta`. ~40–80 lines in one file, with
four gates (adiabatic A/B at loose rtol, forced-thermal parity,
magnetic-deck parity since the branch is shared, `make check`).

Recommendation, accepted into the register: **park for the release**
(P3, symptom-free, mitigation verified twice by execution), land A′
post-release as a one-day change. The row's remedy note was corrected
this session so the eventual taker is not sent down the IWG-scale path.
Literature anchor: Bathe 2016 §8.4.1 (incremental-iterative scheme) and
§8.4.4 Eq. 8.120 (increment-normalized criterion).
