# corc_solder: the "current peak at node 133031" — thin-shell normal-field recovery through an h-conductor

**Date:** 2026-09-01
**Purpose:** Diagnose a suspected current peak in the corc_solder run; record the finding and the blind three-voice round.
**Module:** `src/fem/kernel` (`cl_FEM_Calculator`), `src/fem/maxwell` (postprocessor), example `examples/corc_solder`

## Question
Christian saw a current peak at NodeID 133031 (then 133030, ParaView hover id 29021 = block-local index) in `corc.e-s.00001` of the running corc_solder job (8 ranks, started 18:38, first save t = 0.1 s) and asked: post-processing artifact or problem?

## Answer
- **The node is not a peak.** Interior of its 1-ring in J, J/Jc, H, B, φ (verified with scipy/h5py; confirmed blind by Codex-sol and Grok). It is a mid-tape node on the layer-1 YBCO/buffer sheet, 1 mm from the output terminal; the colour map is dominated by the terminal |J| (8e7 A/m²) and by the feature below.
- **The real anomaly:** helical strips on ~22 % of the layer-1 sheet with |H| = 475–1520 A/m (B up to 2 mT) at I = 0.15 A, one per tape, ≥ 99.9 % radial. Edge dofs (`memdump.hdf5:/fields/edge_h`) are clean (0.5 A/m median, same as the quiet sheet), so it lives only in the recovered normal component.
- **Mechanism (verified, and independently reconstructed by Codex-sol):** the solder annulus (`conductor : solder`, block 2) is an h-conductor with no φ dofs, yet it is the **master** volume of every tape facet. `compute_hn` (`cl_FEM_Calculator.hpp:2599-2633`) recovers h_n = ½(−∇φ_m − ∇φ_s)·n from the nodal `phi` field of both volumes regardless of domain type. Solder-only nodes hold φ = 0 (initialiser); the 1452 layer-0 tape-gap nodes are shared with the bore air at φ ≈ −0.668 A; the annulus is one element (0.22 mm) thick, so solder tets touching the layer-1 tape reach those nodes: |∇φ| ≈ 3040 A/m, ½ of it = the 1520 A/m plateau. 1593/1594 strip nodes have such a bridging tet, 28/5415 quiet nodes do. The strips are the shadows of the layer-0 gaps through the annulus. Not the cut (thin cuts, duplicates jump by exactly I₁), not periodic, not the J/Jc node-sharing leak.
- **Solve exposure:** the same function feeds `compute_h_ts_edge` → `compute_b_ts` → `compute_rho_riva_ts` → jc(|B|, β, T). Today: 2 mT, implied jc 0.15 % low, `element_rho` ≤ 3e-95 — negligible. The strip magnitude is |φ_bore − 0|/(2h), a gauge level of a region with **no pin** (Grok), so its growth is uncontrolled; whether it tracks I is unmeasured. Mainly a post-processing defect at this step; a solve-side risk later.
- `DomainType::InterfaceTsCond` exists but is referenced nowhere; corc_solder is the only deck with a volume conductor next to a thin shell — the path was never exercised.

## R8 double check (same evening) — the bore IS unpinned

Christian challenged the autopin argument and then counted: two disconnected air regions plus six tape buffer layers need eight pins; `corc.bfm` `nodes/pinned` holds seven. Mechanism (Fable, source + data): `find_autopins` (`cl_MaxwellFactory.cpp:3378-3506`) builds the φ-component graph from `Node::node(k)`, filled by `connect_nodes_to_nodes` from every element of the node, conductors included (`cl_Mesh_ConnectivityCalculator.cpp:343-352`). Two air nodes on opposite faces of one solder tet are neighbors; the one-element annulus merges the bore into the outer-air component. Reconstructing that graph from `corc.e-s.00001`: 7 components = 6 buffer layers + one component holding the bore (20767 nodes) and the outer air (39374); the air-only graph separates them. Pins from the `.bfm`: 39368 at r = 7.7 mm in air_03, six non-hanging buffer nodes at z = 0. Earlier readings were wrong on both sides: "39368 is an outer-air node" was right (the exodus has no node id map, so an exodus-index lookup mislabelled it as a layer node for a while), "the autopin catches the bore" was not. Filed as D4 (HIGH); R8 revived; O2 answered. Proposed fix: adjacency from Air/Buffer block elements' node pairs only, plus the existing duplicate and periodic ties. Not applied.

**D4 fix (same evening, approved by Christian as the intended design):** `find_autopins` flags the Air/Buffer elements while tagging their nodes and builds the adjacency by walking `node->element( e )` through flagged elements only — for the node, its duplicates, its periodic partner and that partner's duplicates — instead of the mesh-wide `Node::node( k )` list. Element flags are cleared before and after. Syntax-checked under the build flags; not built. The pin list is persisted in the `.bfm` (`nodes/pinned`), so the corc cache must be regenerated for the fix to reach the run; expected pin count 8.
Audit of the D4 fix (Codex terra/medium, `tmp/ai_exchange/review_autopin_phi_components.md`): sound; node→element incidence complete at the call site, element flag 0 not preserved by any caller (`finalize()` clears it anyway), cut duplicates and periodic partners covered, self-exclusion consistent with the old builder. Expect the pin choice within a component to move where conductor shortcuts used to shorten the sideset distances. Evidence level: static source trace; gates owed: build, regenerated `.bfm`, 8 pins, R6 rerun.

## R7 (2026-09-02) — the "frozen current" was a stale plugin

Evidence: `ramps.hpp` documents that the current period "is not 10 s" (it was, before the 18:41 working-copy edit that set 2 s; first commit at 18:58 already carries 2 s); the job started at 18:38 and loaded the `userdefect.so` built before the edit. A zero-offset logistic depends on t/P only, and 0.1/10 = 0.02/2: I_10s(0.1 s) = 0.072134262796000506 = I_2s(0.02 s), the observed value to all digits. The clock is right (both save files stamp `mTime` = 0.1), the boundary condition is recomputed on every attempt (`cl_FEM_Controller.cpp:243-289, 372-423`, rewind at `:2840`), and the plugin receives the time unchanged (`cl_SourceFunction.hpp:450-452`). No code defect; the run simply rode a 10 s ramp. D2 retracted as a code finding. The rebuilt plugin (21:01) has the 2 s ramp; the cluster rerun needs nothing further. Side note, unproven: save index 1 at t = 0.1 s with "save every 20 ms" in the deck suggests the deck read at 18:38 said 100 ms (`input.conf` modified 19:50).
