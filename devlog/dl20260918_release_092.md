# BELFEM 0.9.2: maintenance release

**Date:** 2026-09-18
**Purpose:** Record how 0.9.2 was cut from `devel` and what gated it.
**Module:** release packaging (`CMakeLists.txt`, `CITATION.cff`, `CHANGELOG.md`)

## What happened

`devel` stood 26 commits ahead of `main` (`84652842`, v0.9.1) at `26bfd28f` with no commit on
`main` that `devel` lacked, so the merge is a fast-forward. The work since 0.9.1: the
`-Wfloat-conversion` clean-up and `-isystem` for third-party headers (`14bb703`), the
quasi-harmonic elastic closure of the pure metals (`2ffebcc`), the MKL PARDISO interface
(`65c38ee`), the two comment sweeps with license headers (`05a4eb5`, `1d67ffe`), the MATLAB
derivation scripts (`08c306b`), the six code-findings tiers of ownership fixes (`70364c1` ..
`26bfd28`), the MPI link probe and rpath pruning (`482ef6b`), the launcher selection (`1dae673`)
and the `CutFactory` 2-D orientation hygiene (`145e2c0`).

Release commit on top of `devel`: version 0.9.1 -> 0.9.2 in `CMakeLists.txt` and
`CITATION.cff` (`date-released` 2026-09-18), and `CHANGELOG.md` `[Unreleased]` -> `[0.9.2]`.
The `[Unreleased]` section had recorded the materials, PARDISO, CMake 4.0, `-isystem`,
`-Wfloat-conversion` and input-range work but none of the code-findings tiers, the MPI
probe/rpath change, the launcher selection, the comment sweeps, the MATLAB scripts or the
`CutFactory` change; those entries were written from the commit messages and the devlogs
and checked against the tree (function names, test files, the four `BELFEM_ERROR` sites).

## Gates

**CI matrix.** The last three nightlies (pipelines 32-34) all ran on `2ffebcc5`; everything
after it was pushed on 2026-09-18 after the 04:03 run, so the tip had never been through the
matrix. Pipeline 35 (source `web`, ref `devel` @ `26bfd28f`, jobs 124-127) was started
2026-09-18 18:41 PDT as the executable gate. 4/4 GREEN at 20:08 PDT (jobs 124-127: 1072 / 1511 / 974 / 1697 s,
about 88 min sequential). The release commit on top differs from `26bfd28f` only in the version
line of `CMakeLists.txt`, `CITATION.cff`, `CHANGELOG.md` and this devlog, so pipeline 35 is the
gate for the tagged code; the 04:03 nightly on `devel` re-runs the matrix on the tagged commit
itself.

**Mandatory homology audit** (rule of 2026-09-13: any `src/homology` edit gets a blind
GPT-6 + Grok cross-audit at xhigh, owner authorization notwithstanding). The `main..devel`
diff touches ten files under `src/homology/`; `scripts/check_comment_only.sh main` confirms
seven of them comment-only and three not: `cl_CutSet.cpp` (destructor deletes `mNodeBitset`,
`70364c1`), `cl_Homology.cpp` (`int tCoeff`, `95809d6`, already audited retroactively on
2026-09-13) and `cl_CutFactory.cpp` (`145e2c0`, whose own jury ran at **high**, not xhigh).
Both auditors got the same seven-claim brief and the full diff, blind.

Codex `gpt-6-astra` xhigh: C1 comment-only, C2 `mNodeBitset`, C3 `tCoeff`, C6 fill-constructed
vectors, C7 no hidden algorithm change: all VERIFIED with file:line evidence. C4/C5 (sense
unchanged; preconditions cannot fire on a previously valid input) REFUTED **for direct calls
of the public method only**: a facet attached with `set_master( master, index, false )` (no
node relink) can have a facet node order that disagrees with the master's edge, and then
`main` (facet order) and `devel` (master order) decide opposite senses; on the factory path
every facet is rebuilt with `set_master()` node-linking before the orientation runs
(`cl_CutFactory.cpp:1517`), so the counterexample is unreachable there. One additional
finding: `cl_CutFactory.cpp:1876` dereferences `tFacet->master()` before the new check, so a
matched facet with a null master (a direct-call state; factory facets all carry a master)
would segfault where `main` computed from the facet nodes. Noted for Christian; no edit made
(closed-module rule, and it is not reachable from the factory). Also noted: under Blaze the
old code read uninitialized components, so a Blaze result may differ from 0.9.1 on the
thin-shell path; that is the fix, not a regression, and the Armadillo path is traced unchanged.

Grok `grok-4.6` xhigh: all seven claims VERIFIED, with the same file:line trail
(2-D element tables put the edge corners in slots 0 and 1, `Facet::set_master( ..., true )`
copies them onto the facet element in that order, and `orient_terminal_curves_2D` is reached
only from `create_thin_shell_cuts` after `duplicate_and_relink_facets`, so on the factory path
the old facet order and the new master order are the same two pointers). Same residual as
Codex, found independently: no `has_master()` test before `tFacet->master()` at `:1876`, not
reachable from a shipped 2-D thin-shell deck. Also noted, pre-existing and outside the diff: the
3-D sibling `orient_terminal_curves` (`cl_CutFactory.cpp:1713-1719`) still size-constructs its
vectors. Deck verdict: no generator, cut-set or orientation change for the shipped examples on
Armadillo; a Blaze run of a 2-D thin-shell deck could differ only where `main` read
uninitialized memory. Both auditors: no defect that needs a change before release.

**Changelog sweep** (Codex `gpt-6-astra` high, read-only): seven factual corrections applied
(the thermal-equation entry had the defect backwards; `T_max` is a table/validity limit, not a
runtime cutoff; the `get_int` range check runs per call; the unit-exponent check does not
reject a numeric prefix with trailing junk; the launcher searches the wrapper dir and its symlink
target in one call; the orientation doc lives under `src/fem/maxwell/doc/`; the string helpers
use integer arithmetic rather than casts), seven overstatements softened, three user-visible
changes added (factories non-copyable, `Metal::create_mech` signature, `pardisotools_solve`
mutable RHS and `pardisotools_get_determinant` removed), three language nits taken.

## Release steps

Christian approved the changelog and delegated the rest ("if all tests pass, do the rest of
the release without me"). Steps, in order, all from the scratch clone of the GitLab bare repo:
release commit on `devel`; `main` fast-forwarded to it; annotated tag `v0.9.2`; `devel`, `main`
and the tag fetched into GitLab through a git-owned staging bare repo (`fetch_as_mirror`, as
for 0.9.1); `/usr/local/sbin/belfem-mirror-github.sh` pushed `main` + tag to GitHub;
`git archive --prefix=belfem-0.9.2/ v0.9.2 | xz -9` from the GitLab bare repo into
`/var/tmp/belfem-release/` with a `.sha256`; `gh release create v0.9.2 --verify-tag` with the
changelog section as notes and both files attached; GitLab release on the same tag with the two
files uploaded and linked afterwards (`release.links.create!`, the 19.2 trap); website
`index.html` (version, date, nineteen decks, download button) and the `/download/` redirect
widened to `0.9.[012]`, `apachectl configtest`, `systemctl reload httpd`, both redirects
curl-checked. The audit records live in `/var/tmp/belfem-release/audits-0.9.2/`.
