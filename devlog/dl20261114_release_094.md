**Purpose:** Record how 0.9.4 was cut from `devel`, what gated it, and what the gates left open.

**AIs involved:** Claude Opus 5.5 (release session, changelog), Claude subagents for the gates: Opus 5.5

**Approved by:** gvallone (release owner since 2026-11-14)

## What happened

`devel` stood at `1d68c58`, 103 commits after v0.9.3. Release commit on top of `devel`:
`CITATION.cff` 0.9.3 -> 0.9.4 (`date-released` 2026-11-14), the `[0.9.4]` section of `CHANGELOG.md`
written from scratch (there was no `[Unreleased]` section), and this entry.

From this release on, `main` carries one commit per release. The 0.9.4 commit on `main` holds exactly
the tree of the release commit on `devel`, has the 0.9.3 release commit as its parent, and carries the
changelog section as its message; the development commits stay on `devel` in GitLab and are not
mirrored. The published tags v0.9.0–v0.9.3 are unchanged.

## Gates

**CI.** Pipelines 101, 102 and 103 passed all four jobs (debug and release, Armadillo and Blaze,
`make check`) on `1d68c58`. The release commit changes only the version record, the changelog and
this devlog.

**Homology audit.** Code under `src/homology` changed in two commits since v0.9.3: `1109752`
(`CutFactory::cuts()`, `mCuts` and the Maxwell retyping loop removed) and `c908dc1`
(`mPeriodicFactory = nullptr`). The cohomology core is unchanged. Neither Codex nor Grok is available
to the release owner, so the blind cross-audit was run by two Claude subagents on different models,
Opus 5.5 and Fable 5.2, each at maximum effort, each given only the brief and a read-only checkout,
neither shown the other's answer. Both confirmed all seven claims: `mCuts` was never filled, so the
removed loop never ran and no result changes; no reference to `cuts()` remains in the public tree; the
`DomainType::Cut` dof-table branch is unreachable and harmless; no in-tree path read the uninitialised
periodicity pointer; the core is untouched. Brief and answers:
`/var/tmp/belfem-release/audits-0.9.4/`. Whether nonfree code calls `cuts()` could not be checked;
the nonfree tree is not part of this checkout.

**Commit review.** No review had run since 0.9.3, so all code commits in `v0.9.3..1d68c58` were
reviewed (homology excluded, covered above). No blocker. One should-fix (F1 below, shipped as a known
issue by the release owner's decision); the other findings are notes, listed under Open.

**Changelog.** A second reader checked every bullet against the source. It found one false claim
(nodal recovery was credited with the memory growth reported after 0.9.3; that growth was
attributed to the wider vertex counters), an incomplete list of changed results in the intro, about
ten overstated bullets and six omitted user-visible changes. All were corrected before approval.

## Open

Filed, not fixed:

- **F1 (known issue, in the changelog).** `004fcf2`, `src/mesh/cl_Mesh_ExodusWriter.cpp:495-503`: a
  3D mesh with a sideset on a 2D (TRI or QUAD) element stops when the Exodus file is written, after
  the solve. 0.9.3 wrote the file. Check at mesh load, or skip and warn, once shell side numbering
  is decided.
- `src/fem/thermal/matrices/mt_thermal_phi.cpp:30-41` (`c0bc009`): a material with neither `density`
  nor `ref_density` gives a NaN thermal mass in release builds (debug assert only). A `BELFEM_ERROR`
  would be safer.
- Armadillo `Vector` transposes only element-wise and transpose row expressions in; Blaze transposes
  every row expression (`cl_AR_Vector.hpp:173-214`, `cl_BZ_Vector.hpp:420-432`). No current consumer
  is affected; with release conformance checks off on Armadillo, only a debug build catches it.
- `tests/linalg/test_CheckPolicy.cpp:31` stops a debug build with `#error` if the Armadillo in use
  does not know `ARMA_CHECK_CONFORMANCE`; only Armadillo 15.6 was available to check.
- Blaze with Clang/AppleClang: the `BELFEM_GCC` guards around the `Matrix` compound operators are
  gone; all gates used GNU.
- Homology documentation: `doc/input_schema.yaml:1296-1297` says `DomainType::Cut` stays live for
  internally generated cuts, and `src/homology/doc/homology_usage_guide.md:317-319, :1246` and
  `src/fem/maxwell/doc/README.md:259` say a `Cut`-typed sideset would get dofs. Neither holds: the
  Maxwell selection admits neither `Cut` nor `Default`, and `FieldList::Cut` is never filled. What
  `Default` protects is the `cut_<n>` label (the renaming loop in `set_block_and_sideset_names`).
- Dead code left in `CutFactory`: `create_cut_sideset_2d/3d` (no caller), `thin_shell_boundaries()`
  and `mThinShellBoundaryIDs` (never filled), `mThinShellBoundaries`, `mOuterBoundaries`.
  `src/homology` is closed to unreviewed edits; removal needs its own audit.
- `todo/deferred/2d_thinshell_todo.md:185-187` (B5) is done by `1109752` but still open, and
  `todo/thick_cut_overlay_block.md:161` still cites `cuts()`.
