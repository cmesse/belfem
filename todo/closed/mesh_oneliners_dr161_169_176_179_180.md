## 2. Architecture: Why "Mirror the Bottom List" Is the Right Spine for DR-161

Two candidates were weighed:

- **A — refuse in top (chosen).** `get_top_nodes` switches on `aElement->type()` with exactly the
  labels `get_bottom_nodes` carries, grouped into the same three geometry arms. A type then has both
  faces or neither; the accept list is pinned by the test's two parameter lists.
- **B — support in bottom.** QUAD8 is free (its bottom is the QUAD9 arm: node 4 is (0,−1),
  `cl_IF_QUAD8.hpp`). QUAD16 needs a new bottom arm *and* a type-aware second swap in the top arm.
  HEX64 needs a 16-index bottom arm. All of it serves no consumer: the only production callers are
  the four Maxwell thin-shell hang helpers (`cl_MaxwellFactory.cpp:1856`, `:1930`, `:1992`,
  `:2099`), which see thin-shell layer elements, and the only other callers are the two tests.

A wins on three grounds: it is the smaller diff, it removes a silently wrong result (QUAD16) instead
of adding untested index tables, and it costs nothing to reverse — the derived Option B indices are
recorded in Appendix A so a future QUAD16/HEX64 thin-shell family can adopt them in one sitting.
Confidence in "no production caller passes the three types": **medium** — the grep over `src/`,
`tests/` and `nonfree/` (§1 citations) is complete, but I did not trace which element types
`ThinShellFactory` can emit; the register row's own claim ("the Maxwell hang helpers only see the
thin-shell families") is the basis.

For the other four rows the spine is simply the sibling that already does it right: the
pointer-keyed `reset_source_container()` (`cl_Mesh_Basis.cpp:278-290`) and the dof container
(`cl_Mesh_Basis.hpp:290-296`) for DR-169; the interpolation factory's `HEX8 / HEX8TS / HEX8TB`
grouping (`cl_IF_InterpolationFunctionFactory.cpp:204-208`) for DR-176; the `find_face_owners`
comparisons that already use `gNoID` (`cl_FaceFactory.cpp:359`, `:395`) for DR-179; and the
`is_terminal()` predicate that already treats `mSideSetB == nullptr` as a legal state
(`cl_Curve.hpp:221-225`) for DR-180.

### 3.1 Cross-cutting findings

- **Sentinel width is a build-configuration property, not a code property.** `gNoID` and `gNoIndex`
  are equal on every tree Christian builds today and differ only under `-DUSE_MKL_64BIT_API=ON`.
  Every `id_t`-against-`gNoIndex` comparison is therefore invisible to the suite. DR-179 fixes the one
  in `create_faces_3d`; the same question extends to `Face`, whose index members are `uint`
  (`cl_Face.hpp:32-38`; the ctor parameters at `:50-54`) and received `gNoIndex` narrowed — traced
  and fixed in R4 (one genuine compare mismatch plus three `-Werror=overflow` sites under INT64).
- **The memory note "PENTA6TS/HEX8TS facet numbering differs from PENTA6/HEX8" is stale for the
  node tables.** `cl_Element_HEX8TS.hpp` and `cl_Element_HEX8.hpp` carry identical
  `get_nodes_of_facet` tables for all six facets (read this session). Only the node tables match:
  the templates are `< 8, 8, 8, 6, 1 >` vs `< 8, 8, 12, 6, 6 >`, so the edge count (8 vs 12) *and*
  the face count (1 vs 6) differ; HEX8TB is `< 8, 8, 4, 6, 1 >`. `create_unity_nodes` reads the node
  table only, so the grouping in R3 is unaffected. The thin-shell canonicalization comment sits at
  `tests/mesh/test_MeshEntities.cpp:76-78`; HEX8TS and HEX8TB are absent from that catalog.
  Confidence **high**.
