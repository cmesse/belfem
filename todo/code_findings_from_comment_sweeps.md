## 1. Findings

- [ ] **F1 — `fn_Mesh_integrate_scalar_over_sidesets.cpp:167-171` broadcasts the master rank, not the value.** The integral is computed inside `if ( rank == aMasterRank )`, then `proc_t tMasterRank = aMasterRank; broadcast( tMasterRank );` and `return aValue;`. Every non-master rank returns its untouched `aValue`. Callers that read the value off rank 0 get zero silently. Behavior-altering fix (`broadcast( aValue, aMasterRank )`), needs a test that checks the value on a non-master rank. Confidence high (lines read). Found by Codex.
- [ ] **F2 — `cl_IWG.hpp:820-821` declares `const Matrix< real > & N( const uint & aIntegrationPoint );` and nothing defines it** (grep over `src/fem/iwg/*.cpp`). A public declaration that cannot link; the working equivalent is `Calculator::N`. Fix: delete the declaration. Trivially safe, but it is code; do it with F3 in one audited commit. Found by the Claude subagent.
- [ ] **F3 — `cl_SolverWrapper.hpp:74-75` `mX`, `mY` are never assigned** anywhere in `src/sparse`; `x()`/`y()` (`:438,446`) dereference null. Either dead (delete members and accessors) or a lost contract (a subclass should set them). Grep for callers of `x()`/`y()` first. Found by the Claude subagent and Grok.
- [ ] **F4 — `IWG::collect_node_coords` (`cl_IWG.cpp:1624`) loops `i <= mNumberOfSpatialDimensions`** and writes `nDim + 1` columns into `aX`. No in-tree caller (the sideset integrator calls the free `collect_node_coords` of `geometrytools.hpp`), but `src/fem/iwg/doc/iwg_usage_guide.md` advertises it, so a user with an `nDim`-column matrix writes out of bounds. Fix: `<` and a bounds assert, or retire the function with the guide entry. Found by the Claude subagent.
- [ ] **F5 — `cl_Element_PENTA6TS.hpp` carries two include guards** (`CL_ELEMENT_PENTA6TS_HPP` and `BELFEM_CL_ELEMENT_PENTA6TS_HPP`), harmless, carried over from sweep 1's O6 pass. Obvious fix; can ride with F2.
- [ ] **F6 — `tests/` was outside both sweeps:** `tests/physics/backendfree/test_MaterialBackendFree.cpp:18` cites a date, `tests/fem/test_EdgeFunctions.cpp:32` cites `tmp/tet10/tet4_circulation_probe.py`. Comment-only; a small batch of its own after sweep 2.
- [x] **F8 — abstract nodes filled past the owner.** REFUTED 2026-09-17 by two independent deep scans (Codex `gpt-6-astra`/high, Grok `grok-4.6`/high, both verified by Claude against `cl_CutProcessor.cpp:1209-1230`): `CutProcessor::collect_duplicates()` appends every abstract node to `Mesh::nodes()` before the factory moves the pointer list, so `~Mesh` deletes them once through `mNodes`; `set_abstract_nodes()` is an unused alternate adopter, and calling it on top of the append would double-insert and double-free. The sweep-2 comment on the member that produced the finding was wrong and is corrected (comment-only). Both scans found the real leak F10 instead. Original text: `Mesh::set_abstract_nodes()` adopts nodes into `mNodes` (`cl_Mesh.cpp:2196-2205`) and nothing in `src/` calls it; `CutFactory` moves freshly allocated nodes (`cl_CutProcessor.cpp:817`) straight into the mesh's abstract-node list (`cl_CutFactory.cpp:439`), and `~Mesh` deletes `mNodes` only. Either those nodes leak, or another owner deletes them; find out, then route them through the adopting setter or document the owner. Found by Codex in the sweep-2 C3 check. Confidence high on the call graph, unknown on the leak.
- [x] **F9 — chained kernel allocates a placeholder mesh nobody deletes.** CONFIRMED 2026-09-17 by two independent deep scans (Codex `gpt-6-astra`/high; Grok `grok-4.6`/high on the third attempt, the first two hit its turn limit), both prescribing the same one-line fix, both verified by Claude at the cited lines. Applied: `mOwnMesh = true ;` after the placeholder allocation on the chained worker branch only. Chain: `ThermalFactory` builds `KernelParameters( aMagneticKernel )` (`cl_ThermalFactory.cpp:34-42`), so the child's `mMesh` before the swap is the parent's worker submesh (`cl_FEM_KernelParameters.cpp:208-210`), owned by the parent (`mOwnSubmesh` set on the distributing path); the placeholder `new Mesh( dim )` is read by `create_equation()` through `IwgFactory` for its dimension, so it cannot simply be dropped. Minimal fix per Codex: `mOwnMesh = true ;` right after the allocation at `cl_FEM_Kernel.cpp:698`, nothing else; `~Kernel` then deletes only the placeholder. No chained-kernel test exists; the deck is `examples/tapestack3d` at two ranks under Valgrind (expected: one `Mesh` from `distribute_mesh():698` per worker before, none after). Grok adds: the placeholder is write-only on the actual coupled path (the thermal factory never calls `create_equation`), `tapestack3d_quench` and `tape_quench_usermat` also exercise the chain, and `mOwnMesh` must never be armed on rank 0 or the unchained path (it would delete the file mesh). Gate: VERIFIED 2026-09-17, Valgrind on `tapestack3d` at two ranks (one timestep, debug tree): `distribute_mesh():698` in no loss record on either rank; the same run confirms F13 (rank 1: 1,456 B definitely lost from `MaxwellFactory::MaxwellFactory`, the worker's empty mesh) and finds F17. Original text: On a worker chained onto a parent kernel, `distribute_mesh()` does `mSubMesh = mMesh; mMesh = new Mesh( dim );` (`cl_FEM_Kernel.cpp:697-699`); `~Kernel` deletes `mMesh` only under `mOwnMesh`, which nothing sets, and `mSubMesh` only under `mOwnSubmesh`, set only on the fresh-distribution path (`:674-680`). The empty placeholder leaks. Found by Codex in the sweep-2 C4 check. Confidence high.
- [ ] **F10 — `CutSet::~CutSet` leaks `mNodeBitset`.** The constructor allocates `mBitset` and `mNodeBitset` (`cl_CutSet.cpp:28-31`), the destructor deletes only `mBitset` (`:35-38`); one `DynamicBitset` with its buffers leaks per cut set on every cut run. `cl_CutSet` is in `src/homology` but not one of the six closed units. Fix: `delete mNodeBitset;` in the destructor. Found independently by Codex and Grok in the F8 scans; verified by Claude. Applied 2026-09-17 into the tier-1 diff; Codex audit of the one-liner: correct. VERIFIED 2026-09-17: Valgrind on `dipole` (one timestep, debug tree) shows `cl_CutSet.cpp:31` in no loss record; the abstract nodes of `cl_CutProcessor.cpp:817` appear only as indirectly lost through the leaked master mesh (F16), consistent with the F8 verdict.
- [ ] **F11 — the thermal equation leaks.** `ThermalFactory` allocates `IWG_MaxwellThermal` (`cl_ThermalFactory.cpp:162`), hands it to `create_field()` (`:169`), which links but does not adopt, then sets `mOwnThermalEquation = false` (`:170`) so its own destructor skips the delete; no `add_equation()` call registers it with the kernel. Leaks on every rank of a coupled run. Found by Codex in the F9 scan; verified by Claude at the cited lines. Fix candidates: `add_equation()` before `create_field()`, or keep factory ownership. Needs its own plan + jury (ownership change).
- [ ] **F12 — the thermal boundary-condition factory leaks.** `create_bc_factory()` returns a `new ThermalBoundaryConditionFactory` (`cl_ThermalFactory.cpp:309-320`) stored as a raw pointer and never deleted (destructor `:45-62` has no delete for it); the conditions themselves are transferred to the kernel. Found by Codex; verified by Claude. Fix: delete it in the destructor or hold it by value. Plan + jury.
- [ ] **F13 — the magnetic worker's original empty mesh leaks.** `MaxwellFactory` allocates `mMesh = new Mesh( mMeshDimension, 0 )` on workers (`cl_MaxwellFactory.cpp:108`), passes it through `KernelParameters( mMesh )` (`:248`), and neither the factory destructor (`:259-299`) nor the kernel (`mOwnMesh` never set) deletes it; also in magnetic-only runs. Found by Codex; verified by Claude (no `delete mMesh` in the factory). Plan + jury together with F9, since both touch `mOwnMesh`.
- [ ] **F14 — `Element::relink_dofs` leaks its malloc.** Valgrind on `dipole`: 8,712 B in 363 blocks plus 144 B in 6 blocks definitely lost, allocated by `malloc` in `Element::relink_dofs()` and reached from `DofManager::consolidate_dofs()` (`cl_FEM_DofManager.cpp:1322`) during `set_equation()`. One block per element consolidated; needs the function read for what the buffer is and who should free it. Found by the F10 Valgrind gate 2026-09-17. Plan + jury.
- [ ] **F15 — one `Calculator` of a sideset group leaks.** 1,464 B definitely lost from `Group::create_calculator()` (`cl_FEM_Group.cpp:128`) for a `SideSet` built in `SideSetData::create_sidesets()` (`cl_FEM_DofMgr_SideSetData.cpp:171`); exactly one block on `dipole`, so probably one group type whose destructor does not delete its calculator, or a replaced calculator. Found by the F10 Valgrind gate. Plan + jury.
- [ ] **F16 — 2.9 MB indirectly lost on the master of `dipole`, root unresolved.** The abstract nodes of `cl_CutProcessor.cpp:817` and, by the total, most of the mesh entities are reported indirectly lost, but no definitely-lost record in the log is a `Mesh` allocation: the largest definitely-lost BELFEM blocks are the `relink_dofs` arrays (F14) and the calculator (F15), the rest is Open MPI/PMIx initialization. So the owner chain that Valgrind considers lost is not the file mesh itself; it needs a run with `--show-reachable` and a look at which lost root the node blocks hang from. Both F9 scans separately claimed the master's file mesh has no deleter (`MaxwellFactory` loads it, hands it through `KernelParameters( mMesh )`, and neither it nor the kernel deletes it); that claim is still unverified by the gate. Plan + jury together with F13.
- [ ] **F17 — 120 B definitely lost at `Kernel::distribute_mesh()` line 652 on rank 0** of `tapestack3d`, on the fresh-distribution path (the partitioning block; lines 646-647 of the same function also root 5.7 MB of "possibly lost" partition buffers). Found by the F9 Valgrind gate 2026-09-17. Read the function before judging. Plan + jury with F13.
- [ ] **F7 — closed cohomology core narration for Gregory** (report only, no AI edit): `cl_Homology.cpp:26` narration, `:45` a commented-out `delete tHomology` fused into a banner, `:82,103,142,147` and `cl_Cohomology.cpp:92,113,151,159` "loop over all dimensions", `cl_SimplicialComplex.cpp:44-100` "delete pointers"/"delete map" ownership facts in narration form; plus sweep 1's §6 TODO list. Found by Grok.
