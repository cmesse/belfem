## 1. Findings

- [x] **F1 — `fn_Mesh_integrate_scalar_over_sidesets.cpp:167-171` broadcasts the master rank, not the value.** The integral is computed inside `if ( rank == aMasterRank )`, then `proc_t tMasterRank = aMasterRank; broadcast( tMasterRank );` and `return aValue;`. Every non-master rank returns its untouched `aValue`. Callers that read the value off rank 0 get zero silently. Behavior-altering fix (`broadcast( aValue, aMasterRank )`), needs a test that checks the value on a non-master rank. Confidence high (lines read). Found by Codex.
- [x] **F2 — `cl_IWG.hpp:820-821` declares `const Matrix< real > & N( const uint & aIntegrationPoint );` and nothing defines it** (grep over `src/fem/iwg/*.cpp`). A public declaration that cannot link; the working equivalent is `Calculator::N`. Fix: delete the declaration. Trivially safe, but it is code; do it with F3 in one audited commit. Found by the Claude subagent.
- [x] **F3 — `cl_SolverWrapper.hpp:74-75` `mX`, `mY` are never assigned** anywhere in `src/sparse`; `x()`/`y()` (`:438,446`) dereference null. Either dead (delete members and accessors) or a lost contract (a subclass should set them). Grep for callers of `x()`/`y()` first. Found by the Claude subagent and Grok.
- [x] **F4 — `IWG::collect_node_coords` (`cl_IWG.cpp:1624`) loops `i <= mNumberOfSpatialDimensions`** and writes `nDim + 1` columns into `aX`. No in-tree caller (the sideset integrator calls the free `collect_node_coords` of `geometrytools.hpp`), but `src/fem/iwg/doc/iwg_usage_guide.md` advertises it, so a user with an `nDim`-column matrix writes out of bounds. Fix: `<` and a bounds assert, or retire the function with the guide entry. Found by the Claude subagent.
- [x] **F5 — `cl_Element_PENTA6TS.hpp` carries two include guards** (`CL_ELEMENT_PENTA6TS_HPP` and `BELFEM_CL_ELEMENT_PENTA6TS_HPP`), harmless, carried over from sweep 1's O6 pass. Obvious fix; can ride with F2.
- [x] **F6 — `tests/` was outside both sweeps:** `tests/physics/backendfree/test_MaterialBackendFree.cpp:18` cites a date, `tests/fem/test_EdgeFunctions.cpp:32` cites `tmp/tet10/tet4_circulation_probe.py`. Comment-only; a small batch of its own after sweep 2.
- [x] **F8 — abstract nodes filled past the owner.** REFUTED 2026-09-17 by two independent deep scans (Codex `gpt-6-astra`/high, Grok `grok-4.6`/high, both verified by Claude against `cl_CutProcessor.cpp:1209-1230`): `CutProcessor::collect_duplicates()` appends every abstract node to `Mesh::nodes()` before the factory moves the pointer list, so `~Mesh` deletes them once through `mNodes`; `set_abstract_nodes()` is an unused alternate adopter, and calling it on top of the append would double-insert and double-free. The sweep-2 comment on the member that produced the finding was wrong and is corrected (comment-only). Both scans found the real leak F10 instead. Original text: `Mesh::set_abstract_nodes()` adopts nodes into `mNodes` (`cl_Mesh.cpp:2196-2205`) and nothing in `src/` calls it; `CutFactory` moves freshly allocated nodes (`cl_CutProcessor.cpp:817`) straight into the mesh's abstract-node list (`cl_CutFactory.cpp:439`), and `~Mesh` deletes `mNodes` only. Either those nodes leak, or another owner deletes them; find out, then route them through the adopting setter or document the owner. Found by Codex in the sweep-2 C3 check. Confidence high on the call graph, unknown on the leak.
- [x] **F9 — chained kernel allocates a placeholder mesh nobody deletes.** CONFIRMED 2026-09-17 by two independent deep scans (Codex `gpt-6-astra`/high; Grok `grok-4.6`/high on the third attempt, the first two hit its turn limit), both prescribing the same one-line fix, both verified by Claude at the cited lines. Applied: `mOwnMesh = true ;` after the placeholder allocation on the chained worker branch only. Chain: `ThermalFactory` builds `KernelParameters( aMagneticKernel )` (`cl_ThermalFactory.cpp:34-42`), so the child's `mMesh` before the swap is the parent's worker submesh (`cl_FEM_KernelParameters.cpp:208-210`), owned by the parent (`mOwnSubmesh` set on the distributing path); the placeholder `new Mesh( dim )` is read by `create_equation()` through `IwgFactory` for its dimension, so it cannot simply be dropped. No chained-kernel test exists; the deck is `examples/tapestack3d` at two ranks under Valgrind (expected: one `Mesh` from `distribute_mesh():698` per worker before, none after). Grok adds: the placeholder is write-only on the actual coupled path (the thermal factory never calls `create_equation`), `tapestack3d_quench` and `tape_quench_usermat` also exercise the chain, and `mOwnMesh` must never be armed on rank 0 or the unchained path (it would delete the file mesh). The empty placeholder leaks. Found by Codex in the sweep-2 C4 check. Confidence high.
